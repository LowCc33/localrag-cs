# 议价 Step1 偏好识别失效 + 重复话术修复

## 【环境信息】
- 代码路径：`~/localrag-cs/`
- venv：`~/localrag-cs1/venv/`
- 核心文件：`customer_service/engine.py`（4826行，客服引擎核心）
- 店铺配置：`customer_service/shops/weimusi.json`（维慕斯全铝，用于测试）
- 店铺模板：`customer_service/shops/weimusi_templates.yaml`

## 【问题描述】

场景：用户第一轮问「多少钱一平？」→ 客服报价格区间（bargain_step=1），第二轮用户说「档次高点的，做橱柜和衣柜」

实际表现（3个bug叠加）：
1. 没有识别到「档次高点的」= 品质偏好
2. 没有识别到「橱柜和衣柜」= 两个场景，应该走多场景推荐矩阵
3. 最终回复复读了一遍价格区间，还重复问"您看重哪方面，做哪些地方的柜子"（和第一轮话术重复）

预期表现：识别品质偏好 + 多场景 → 走推荐矩阵，给橱柜和衣柜分别推高端材料并报实价，推进到 Step2

## 【根因分析】

### Bug1：品质偏好关键词缺失
`_detect_preference_type`（engine.py 约1476行）的 `quality_keywords` 里没有「档次高」「档次高点」「高档次」这类表达，导致用户说"档次高点的"检测不到品质偏好。

### Bug2：意图分类错判为 product_type
LLM 19类细分类（`classify_intent_detail`）把「档次高点的，做橱柜和衣柜」归为 `product_type`。
原因：`product_type` 关键词校验列表（约2722行）里有「橱柜」「衣柜」，用户输入沾边，关键词校验通过，就走了 product_type 分支，没进议价状态机。
实际上用户是在选材料档次+说场景，应该归到价格/选材料类走状态机。

### Bug3：LLM决策超时 → fallback复读价格区间
进入议价v3后，`_llm_bargain_decision`（约3494行）调用火山引擎接口超时（10s），触发 `_bargain_fallback_current_step`（约4043行）。
Step1 的 fallback 直接调用 `_render_bargain_template("bargain_price_range")`，就是完整的价格区间话术，里面又带了"您看重哪方面，做哪些地方的柜子"，造成复读。

注意：Bug3 是偶发的（接口超时），但 Bug1 和 Bug2 是必现的。就算接口不超时，因为意图分类错了，也走不到正确的推荐流程。

## 【修复方案】

### 修复1：补全品质偏好关键词（高优先级）
在 `_detect_preference_type` 的 `quality_keywords` 里补充：
「档次高」「档次高点」「高档次」「档次高点的」「好一点」「好一点的」「好点儿」「好点儿的」「要好的」「要高端」「要高档」

位置：engine.py 约1488-1491行。

### 修复2：Step1 关键词兜底推荐（高优先级）
核心思路：在 `_handle_bargain_v3` 里，调用 LLM 决策之前，先做一次关键词快速检测。如果当前是 Step1 且用户输入里同时有场景词或偏好词，直接走 `_action_recommend_material`，不调用 LLM。

为什么要加：LLM 分类不稳定 + 接口偶发超时，导致 Step1 最核心的"用户选材料档次/说场景"场景经常走丢。Step1 是整个议价流程的入口，必须稳。

实现位置：`_handle_bargain_v3` 函数内，调用 `_llm_bargain_decision` 之前（约4150行附近）。

实现逻辑（伪代码）：
```python
# Step1 关键词兜底：检测到明确的偏好+场景信号，直接走推荐，不调LLM
if self.bargain_step == 1:
    has_preference = self._detect_preference_type(text) is not None
    room_types = self._detect_room_types(text)
    has_scene = len(room_types) > 0

    # 误判防护：排除纯疑问句（无明确选择信号）
    question_words = ["吗", "呢", "怎么", "怎样", "如何", "行不行", "好不好", "怎么样"]
    choice_signal_words = ["要", "选", "用", "想要", "给我来", "来个", "就要", "就用", "就选"]
    is_question = any(w in text for w in question_words)
    has_choice_signal = any(w in text for w in choice_signal_words)

    # 触发条件：(有偏好 或 有场景) 且 不是纯疑问
    if (has_preference or has_scene) and not (is_question and not has_choice_signal):
        tag, reply, state_updates = self._action_recommend_material("")
        return tag, reply
```

说明：
- `_action_recommend_material` 内部已经会调 `_get_recommendation(text)` 从推荐矩阵查，不用额外处理
- 只在 Step1 生效，不影响其他阶段
- 疑问句 + 无选择信号 → 不触发，避免把「品质怎么样」「环保吗」误判成选材料

### 修复3：优化意图分类定义（高优先级）
修改 `classify_intent_detail` 的 `product_type` 分类定义（约2634行），明确边界：

原定义：
13. product_type - 用户问产品种类/业务范围，如能做什么柜子、有榻榻米吗、做橱柜吗

新定义：
13. product_type - 用户纯问产品种类/业务范围/能做什么，如能做什么柜子、有榻榻米吗、你们都做什么
    注意：如果用户是在说"我要做橱柜+衣柜""厨房做什么板材好"这类带选材/价格意图的，归为 price_query，不是 product_type

同时在注意事项（约2642行）里加一条：
- 用户在选材料阶段说场景（如"做橱柜和衣柜""档次高点的，衣柜用什么"），归为 price_query，走议价状态机，不是 product_type

### 修复4：优化议价决策层提示词（中优先级）
在 `_llm_bargain_decision` 的系统提示词里（约3535-3560行），补充 Step1 的动作优先级：

在「选择动作时优先考虑」那段后面加：
- Step1（已报价格区间）时，优先级：
  1) 用户说了场景+偏好 → recommend_material（推荐材料并报实价）
  2) 用户明确说某种材料 → quote_material_price（报指定材料价格）
  3) 用户重复问价格/没听懂 → restate_price_range（重述价格区间）
  不要把"用户说做哪些柜子/选什么档次"当成无关问题，这是在选材料的信号

## 【自测要求】

### 必测用例（全部通过才算完成）

用 weimusi 店铺，会话初始化后按顺序发：

| 轮次 | 用户输入 | 预期 |
|------|----------|------|
| 1 | 多少钱一平？ | 报价格区间，bargain_step=1 |
| 2 | 档次高点的，做橱柜和衣柜 | 推荐高端材料，分别说橱柜和衣柜，推进到 bargain_step=2，不再复读价格区间 |
| 3 | 品质怎么样？ | 回答品质相关问题，不推进状态，不触发推荐 |
| 4 | 环保吗？ | 回答环保相关问题，不推进状态，不触发推荐 |
| 5 | 性价比高的，做衣柜 | 推荐性价比材料，推进到 Step2 |
| 6 | 你推荐吧，做全屋 | 推荐主推材料，推进到 Step2 |

### 验证方法

写个简单的测试脚本或者直接用 Python 交互，按上面6个用例跑一遍，打印每轮的 tag 和 bargain_step。

重点验证：
1. 第2轮必须命中推荐，tag 是 bargain/recommend_material，bargain_step 变成 2
2. 第3、4轮（疑问句）不能误触发推荐，bargain_step 保持不变
3. 第5、6轮（其他偏好+场景）也要能正常触发推荐

### 不允许的情况
- 把「品质怎么样」「环保吗」这类事实疑问句误判成选材料偏好
- 乱推进状态（比如用户还在问详情直接推进到摸底）
- 影响非 Step1 阶段的正常逻辑
